# VPS Scope

> Аудит безопасности и рабочего состояния VPS с собственными прокси, туннелями и приватными сетями.

VPS Scope работает на Ubuntu и Debian. Сначала он проверяет базовую безопасность хоста: учётные записи и SSH, sudo, брандмауэр, защиту от перебора, обновления, пакеты, службы systemd, Docker, сертификаты TLS, журналы, ресурсы и признаки подозрительного закрепления. Эти результаты полезны и для сервера без прокси.

Для прокси-сервера этой общей основы недостаточно. Публичный порт может быть ожидаемым входом Reality, Hysteria2 или Shadowsocks, а может принадлежать панели управления, подписке или внутреннему API, которые не должны быть доступны всему Интернету.

Таким образом, VPS Scope объединяет состояние хоста Linux и прокси-нагрузку в одну цепочку доказательств: база данных панели и конфигурация прокси показывают, «как должно быть», systemd, Docker, процессы и фактические слушатели — «как всё работает сейчас», а брандмауэр хоста и обратный прокси — «как к сервису можно обратиться извне». В конце отчёт старается дать несколько прямых ответов:

- Существуют ли явные риски для SSH, учетных записей, межсетевых экранов, обновлений и системных служб;
- Действительно ли входы Reality, Hysteria2 и Shadowsocks слушают нужные адреса и согласованы с брандмауэром;
- Были ли случайно открыты панели управления, такие как S-UI и 3x-ui, для всей публичной сети;
- Согласованы ли конфигурация, база данных панели, процессы и фактические слушатели;
- Существуют ли какие-либо проблемы, влияющие на непрерывную работу основных служб, сертификатов TLS, журналов и системных ресурсов.

Это не просто распознавание программ и не сканирование портов с добавленным списком Linux-проверок. Обычный VPS получает базовый аудит хоста, а прокси-VPS — дополнительное объяснение связей между прокси-входами, панелями управления, подписками, управляющими API, контейнерами и обратными прокси.

```bash
curl -fsSL https://github.com/sakkaku404/vps-scope/releases/latest/download/run.sh | sudo bash
```

Эта команда автоматически проверяет SHA-256 загруженного файла и запускает его. Если `cosign` не установлен, выводится короткое предупреждение о том, что подпись издателя не проверена; вводить `continue` больше не требуется.

В интерактивном режиме доступны упрощённый китайский, английский, русский и персидский языки. Для запуска без диалога используйте `--lang zh-CN`, `--lang en`, `--lang ru-RU` или `--lang fa-IR`.

Чтобы пропустить вопросы, укажите параметры аудита после `bash -s --`. Параметры, начинающиеся с `--`, автоматически передаются команде `audit`:

```bash
curl -fsSL https://github.com/sakkaku404/vps-scope/releases/latest/download/run.sh | sudo bash -s -- --lang ru-RU --profile proxy
```

По умолчанию результат отображается только в терминале, а файлы отчёта не создаются. Чтобы сохранить HTML, Markdown и JSON, выберите вариант вывода 2 или 3. VPS Scope не содержит исправлений и не изменяет SSH, брандмауэры, службы, учетные записи или пакеты.

По умолчанию аудит также не запускает исполняемые файлы S-UI, 3x-ui, sing-box, Xray, Nginx и других проверяемых компонентов: он только читает конфигурацию, базы данных и текущее состояние системы. Лишь явно заданный параметр `--native-self-test` запускает эти программы после проверки владельца и прав; сторонний код получает права процесса аудита, то есть root при запуске через `sudo`.

## Реальный пример

Следующее взято из тестового VPS под управлением S-UI 1.5.3 и sing-box, без адреса и ненужной информации:

```text
Заключение по прокси-VPS
────────────────────────────────────────────────────────────────────
Обнаружено: S-UI, sing-box
Входы прокси       PASS
  Подтверждены 4 входа; конфигурация, активные слушатели и брандмауэр согласованы.
Панель управления  RISK/HIGH
  S-UI 56709/tcp · публичный wildcard · разрешено брандмауэром
  TLS включён · путь нестандартный · панель доступна из всего Интернета
Конфигурация       INFO
  Конфигурация разобрана статически; программы панели и прокси не запускались.

Входы прокси:
  443/tcp    sing-box/vless (reality)       публичный · разрешено · PASS
  443/udp    sing-box/hysteria2             публичный · разрешено · PASS
  32003/tcp  sing-box/shadowsocks           публичный · разрешено · PASS
  32003/udp  sing-box/shadowsocks           публичный · разрешено · PASS
```

Одна панель и один процесс ядра могут использовать несколько публичных портов. Обычный аудит VPS часто описывает их просто как открытые порты. VPS Scope сопоставляет базу панели, конфигурацию прокси, процессы, слушатели и брандмауэр, чтобы не спутать ожидаемые прокси-входы с панелью управления, которую следует ограничить.

В этом главное отличие от общего аудита VPS: необходимые проверки SSH, учётных записей, обновлений и закрепления сохраняются, но назначение каждого прокси-входа оценивается отдельно.

## Что вы получите после проверки?

По умолчанию результат показывается только в терминале. Если выбрать вариант вывода 2 или 3 либо использовать `--format bundle`, один аудит сохраняет тот же набор результатов в четырех форматах:

```text
report.ru-RU.html   Рекомендуется: скачайте и откройте в браузере
report.ru-RU.txt    Текстовая версия для терминала
report.ru-RU.md     Полный отчёт Markdown
report.json         Полные машиночитаемые данные для сравнения и базовых снимков
manifest.json       SHA-256-манифест четырёх файлов отчёта
```

Другими словами, в каталоге **4 разных формата одних и тех же результатов тестов плюс 1 контрольный список**, а не четыре теста.

`report.json` — каноническая запись аудита, общая для всех форматов. Она содержит 55 стабильных идентификаторов проверок, состояния, уровни серьёзности и коды причин, а также типизированное представление развёртывания: обнаруженные компоненты, конечные точки служб, связи прокси и обратного прокси и степень покрытия доказательствами. HTML, Markdown, сравнение истории и базовые снимки используют эти структурированные данные, а не разбирают текст терминала. Старые отчёты `schema 1.0` остаются читаемыми. `vps-scope verify report.json` проверяет семантический контракт; при проверке полного пакета команда также сверяет набор файлов и SHA-256 с `manifest.json`.

После сохранения программа сначала покажет постоянный путь `latest` к HTML-отчёту. Проще всего открыть SFTP в SSH-клиенте, перейти в `/root/vps-scope-reports/latest/` (для пользователя без root используйте путь, показанный программой) и скачать `report.ru-RU.html`. Также можно выполнить на своём компьютере:

```bash
scp <SSH_HOST>:'/root/vps-scope-reports/latest/report.ru-RU.html' .
```

Замените `<SSH_HOST>` на IP-адрес, домен или SSH-псевдоним, который обычно используется для этого VPS. Укажите те же порт, файл ключа или настройки `ssh-agent`, что и при обычном входе: VPS не может узнать, где клиент хранит закрытый ключ. Каталог истории с временной меткой и список пяти файлов по-прежнему выводятся ниже.

После временного запуска одной командой файлы отчёта сохраняются, но загруженная программа удаляется. Следующие команды доступны только после установки VPS Scope:

```bash
sudo vps-scope report show  # снова показать последний результат в терминале
sudo vps-scope report path  # показать каталог последнего отчёта
sudo vps-scope report list  # перечислить сохранённые отчёты
```

HTML-отчёт сначала отвечает на пять вопросов: состояние прокси-входов, доступность панели управления, согласованность конфигурации и выполнения, доступность сервисов и базовая безопасность Linux. Затем он показывает рекомендации и технические сведения. Страница поддерживает поиск, фильтр по состоянию и раскрытие доказательств без внешних скриптов и шрифтов.

## Что проверяет VPS Scope

### Прокси-входы и панели управления

- Отличает прокси-входы, панели управления, точки подписки и управляющие API.
- Сопоставляет конфигурацию протокола, TCP/UDP-слушатели, владельца процесса и правила брандмауэра IPv4/IPv6.
- Находит настроенные, но не запущенные входы, блокировку брандмауэром, неверный процесс и слушатели, оставшиеся после отключения.
- Определяет, слушает ли панель публичный адрес, только loopback или опубликована через Nginx, Caddy либо HAProxy.
- Показывает корневой/стандартный путь и состояние TLS, но не считает скрытый URL контролем доступа.

### Конфигурация и статус работы

- По умолчанию статически разбирает конфигурации sing-box и Xray; запуск встроенных самопроверок включается только явно.
- Сопоставляет базы S-UI и 3x-ui/x-ui, сгенерированную конфигурацию, процессы и слушатели.
- Проверяет рабочие связи Reality, Hysteria2, TUIC, Trojan, Shadowsocks, WireGuard и OpenVPN.
- Считает сигналы ошибок аутентификации, рукопожатия, DNS, TLS, маршрутизации и входа в панель, не копируя исходные журналы и данные пользователей.
- Проверяет срок действия сертификата, расписание и последние результаты продления, а также перезагрузку сервиса.

### Docker и системная база

- Проверяет privileged-режим, host network, опасные capabilities, Docker socket и опубликованные порты.
- Сопоставляет INPUT, FORWARD и DOCKER-USER с фактической публикацией контейнеров.
- Проверяет SSH, учётные записи, sudo, Fail2ban/CrowdSec, обновления и службы systemd.
- Проверяет OOM, core dump, заполнение диска и inode, постоянство журналов и подозрительные автозапуски.
- Находит дополнительные UID 0, необычные SSH-ключи, программы из временных каталогов и удалённые исполняемые файлы, которые всё ещё работают.

## Уровень поддержки

Распознавание продукта не означает полной поддержки каждой версии, ветки и схемы развёртывания. Текущая поддержка разделена на три уровня:

### Наиболее полно проверено

- S-UI
- 3x-ui / x-ui
- sing-box
- Xray-core

Эти компоненты проверялись на одноразовых VPS вместе с настоящими базами панелей, конфигурациями, слушателями, брандмауэром и прокси-входами.

### Специализированные адаптеры и проверки

- Hiddify
- Marzban
- Outline
- WireGuard
- OpenVPN
- Hysteria2, TUIC, Trojan, Shadowsocks

### Определение связей развёртывания

- Docker и Docker Compose
- Nginx
- Caddy
- HAProxy

Конкретные версии, способы развёртывания и проверенную семантику см. в документах [Совместимость прокси](PROXY-COMPATIBILITY.md) и [Матрица совместимости](COMPATIBILITY-MATRIX.md). Неизвестная схема базы данных, динамический upstream обратного прокси или неполные доказательства дают `UNKNOWN`, а не ложное подтверждение безопасности.

### Лабораторная проверка

Перед выпуском v1.1.0 пять одноразовых VPS дважды прошли обычный и глубокий аудит, проверку пакета отчёта, создание обезличенного пакета поддержки и межузловые TCP/UDP-пробы. Каждый хост выдал все 55 результатов без расхождений в состоянии, серьёзности, кодах причин и связях конечных точек; хост с 512 МБ памяти также завершил глубокий аудит. После проверки машины, временные правила и вспомогательные процессы были удалены.

Это исторические данные контролируемого испытания, а не гарантия для каждой версии системы, панели или облачной сети. Роли хостов и воспроизводимый контракт описаны в [документе о тестировании](TESTING.md) и [готовности к выпуску](READINESS.md).

## Как понять результаты

Отчёт не выводит необъяснимую числовую оценку безопасности. Используются четыре состояния:

- `PASS`: доказательства подтверждают текущий вывод, но не гарантируют постоянную безопасность сервера.
- `RISK`: обнаружена проблема или условие, требующее проверки.
- `INFO`: инвентаризация или контекст, которые сами по себе не являются проблемой.
- `UNKNOWN`: доказательств недостаточно или их не удалось собрать; это не `PASS`.

При чтении в первую очередь обратите внимание на:

1. **Заключение по прокси-VPS**: в порядке ли прокси-входы и панель управления?
2. **Приоритетные действия**: что следует проверить в первую очередь.
3. **Возможное влияние на доступность**: проблемы входов, брандмауэра, сертификатов или восстановления служб.
4. **Недостаточно доказательств**: часть, по которой инструмент не может достоверно судить.

Окончательный «Индекс результатов проверок» представляет собой справочник состояния 55 проверок. Полные доказательства находятся в HTML, Markdown и JSON.

## Установка и общие команды

Если требуются регулярные проверки, можно установить:

```bash
curl -fsSL https://github.com/sakkaku404/vps-scope/releases/latest/download/install.sh | sudo bash
sudo vps-scope
```

Без параметров откроется интерактивный выбор китайского, английского, русского или персидского языка. Аудит можно запустить и напрямую:

```bash
sudo vps-scope audit --lang ru-RU --profile proxy
sudo vps-scope audit --profile custom --expect-public 22/tcp,443/tcp
sudo vps-scope audit --deep
# Необязательно: запустить встроенные самопроверки доверенных локальных программ
sudo vps-scope audit --native-self-test
```

### Что меняет профиль сервера

Профиль не отключает базовые проверки и ничего не меняет на сервере. Он лишь даёт контекст для оценки того, является ли публичный слушатель ожидаемым для этой машины.

| Профиль | Когда использовать | Как влияет на оценку |
|---|---|---|
| `auto` | Рекомендуется, если вы не уверены | Определяет `general`, `proxy`, `web`, `docker` или `mixed` по процессам, systemd, Docker и известным путям конфигурации |
| `general` | Обычный Linux VPS | Не предполагает наличие публичного прокси-, веб- или контейнерного входа |
| `proxy` | sing-box, Xray, S-UI, 3x-ui, Hysteria2 и похожие серверы | Считает подтверждённые доказательствами прокси-входы ожидаемыми кандидатами, но отдельно проверяет панели, подписки и управляющие API |
| `web` | Nginx, Caddy, HAProxy, Apache и другие веб-фронтенды | Добавляет контекст веб-входа |
| `docker` | Серверы, публикующие сервисы преимущественно через Docker | Учитывает публикацию контейнеров, FORWARD и DOCKER-USER |
| `mixed` | Серверы с несколькими ролями | Объединяет соответствующие контексты |
| `custom` | Вы точно знаете допустимые публичные порты | Требует `--expect-public PORT/tcp,PORT/udp` |

Профиль `proxy` не делает публичную панель управления безопасной. Если сомневаетесь, используйте `auto`: отчёт сохранит и выбранную, и обнаруженную роль.

Интерактивный режим и команда временного запуска по умолчанию показывают отчёт только в терминале. Чтобы одновременно показать и сохранить полный отчёт, выберите вариант вывода 2 или укажите расположение вручную:

```bash
sudo vps-scope audit --lang ru-RU --profile proxy \
  --format bundle --also-terminal --output ./reports/my-vps
```

Если у вас уже есть JSON, вы можете восстановить отчет в автономном режиме без повторного подключения к серверу:

```bash
vps-scope render --lang ru-RU --format html --output report.html report.json
vps-scope verify report.json
vps-scope verify ./reports/my-vps
```

Сравните два результата с одного сервера:

```bash
vps-scope diff old.json new.json
vps-scope baseline create report.json baseline.json
vps-scope baseline check baseline.json report-new.json
```

### Явная политика и проверка с другого узла

Автоматическое обнаружение понимает распространённые панели и прокси-входы, но не знает ваших требований к источникам, TLS, пути панели и маршрутам IPv4/IPv6. Файл политики фиксирует эти ожидания, не содержит учётных данных узлов и ничего не меняет на сервере:

```bash
vps-scope policy init policy.json
# отредактируйте роли, доступность и ожидаемые исходящие маршруты
vps-scope policy validate policy.json
sudo vps-scope audit --profile proxy --policy policy.json
```

Для проверки доступности из другой сети создайте план без секретов на проверяемом VPS, выполните его на другом контролируемом VPS и импортируйте наблюдение:

```bash
vps-scope probe plan --target 203.0.113.10 --output plan.json report.json
vps-scope probe run --output observation.json plan.json
vps-scope probe import --output report-observed.json report.json observation.json
```

TCP сравнивается с заявленной политикой. UDP остаётся `UNKNOWN`: произвольная датаграмма не доказывает успешное рукопожатие Hysteria2, TUIC, WireGuard или другого протокола. `WORK-017` также офлайн сопоставляет версии 3x-ui, sing-box и Xray со встроенным снимком официальных бюллетеней. Совпадение уязвимого диапазона даёт `RISK`, неизвестная версия или устаревшая база — `UNKNOWN`; отсутствие совпадения не означает отсутствие других уязвимостей.

Перед публикацией отчёта создайте обезличенную версию:

```bash
vps-scope redact --format markdown --output public.md report.json
```

Отчеты по-прежнему могут содержать конфиденциальные сведения об отношениях развертывания. Прежде чем делиться ими, просмотрите их самостоятельно. Полные правила см. в [Заявлении о конфиденциальности](PRIVACY.md).

## Область поддержки и ограничения

В настоящее время поддерживается:

- Ubuntu и Debian
- Linux `amd64`, `arm64`
- Обычное развёртывание через systemd и развёртывание в Docker.

VPS Scope может проверять конфигурацию и рабочий статус, видимые внутри VPS, но не может:

- доказать, что сервер точно не скомпрометирован;
- прочитать облачный брандмауэр или security group из гостевой системы;
- заменить проверку настоящим клиентом или наблюдение из другой сети;
- гарантировать правильное понимание новой, ещё не поддержанной схемы панели.

Проверки по умолчанию подходят для регулярного запуска. `--deep` дополнительно проверяет SUID/SGID, файловые capabilities и целостность установленных пакетов, поэтому работает дольше. Не запущенная глубокая проверка отмечается как невыполненная, а не как `PASS`.

## Загрузка и проверка безопасности

Сценарии временного запуска и установки сами являются подписанными файлами Release. После запуска они всегда проверяют SHA-256 загруженного двоичного файла, а при наличии `cosign` — его подпись GitHub Actions без ключа. Без `cosign` временный сценарий выводит короткое предупреждение и продолжает автоматически; `VPS_SCOPE_REQUIRE_SIGNATURE=1` требует успешной проверки подписи и в противном случае останавливает запуск. Постоянная установка по-прежнему требует интерактивного подтверждения, а автоматизация должна явно использовать `--allow-unsigned` или `VPS_SCOPE_ALLOW_UNSIGNED=1`, чтобы разрешить установку только с проверкой контрольной суммы.

Команда `curl | bash` не может проверить загрузочный сценарий до начала его выполнения. Для полной проверки загрузите сценарий фиксированной версии и его Sigstore bundle, проверьте сценарий и только затем запускайте его. Точные команды, сведения о происхождении и лицензиях приведены в [документации по цепочке поставок](SUPPLY-CHAIN.md).

## Почему VPS Scope

VPS Scope появился после практической проверки [vernu/vps-audit](https://github.com/vernu/vps-audit). Этот скрипт упростил самостоятельный аудит VPS, но также показал, что чтение только отдельных файлов конфигурации, произвольные пороги по числу портов или служб и трактовка ошибки сбора данных как безопасного результата приводят к ложным срабатываниям и пропущенным рискам.

Позже фокус проекта постепенно переключился на прокси-серверы. Порт общедоступной сети может представлять собой обычный вход Reality или Hysteria2, либо это может быть панель, интерфейс подписки или внутренний API, доступный всему Интернету. Общая базовая версия Linux по-прежнему необходима, но ее недостаточно для объяснения этих взаимосвязей использования.

VPS Scope не является форком vps-audit; код и логика проверок реализованы независимо.

Спасибо OpenAI Codex за большую часть кода на Go — пока он написал на Go заметно больше, чем сам сопровождающий проекта, который теперь старается во всём этом разобраться.
